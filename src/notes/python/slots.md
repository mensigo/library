## Где живут атрибуты

По умолчанию каждый[^1] экземпляр держит свои атрибуты в `__dict__` — обычном словаре,
который висит на объекте отдельным указателем.

```python plain_user.py
class User:
    def __init__(self, name, age):
        self.name = name
        self.age = age

User("Alice", 20).__dict__
```

::: out
{'name': 'Alice', 'age': 20}
:::

Это удобно: атрибуты можно добавлять на ходу, объект легко сериализовать и осмотреть в отладчике.
Но словарь — это хеш-таблица, а хеш-таблица всегда держит запас пустых ячеек. Пока объектов сотни,
накладные расходы не видны. Когда их миллионы — видны только они.

## Как это выглядит в коде

Решение — объявить в теле класса атрибут `__slots__` с коллекцией имен
(обычно кортеж или список[^2]):

::: split

```python было
class User:

    def __init__(self, name, age):
        self.name = name
        self.age = age
```

```python/1 стало
class User:
    __slots__ = ("name", "age")
    def __init__(self, name, age):
        self.name = name
        self.age = age
```

:::

Снаружи ничего не изменилось: `user.name` и `user.age` читаются и пишутся как прежде.
Изменился способ хранения — вместо записи в словарь это теперь дескриптор, который кладет
значение в конкретную ячейку экземпляра.

::: tip Проверьте на своих данных
Цифры экономии сильно зависят от версии CPython, числа полей и того, что лежит внутри.
Полезнее один раз замерить свой класс, чем опираться на чужие числа.
:::

```python measure.py
import tracemalloc

def measure(cls, n=200_000):
    tracemalloc.start()
    items = [cls("Alice", 20) for _ in range(n)]
    peak = tracemalloc.get_traced_memory()[1]
    tracemalloc.stop()
    return peak / n   # байт на экземпляр

print(measure(User), measure(SlottedUser))
```

::: out идея
сравнивать не абсолютные числа, а отношение между двумя своими классами
:::

## За что платим

### Новые атрибуты

Присвоить экземпляру поле, которого нет в `__slots__`, больше нельзя —
прилетит `AttributeError`. Это ровно та динамика, которую мы обменяли на память.

```python//2 strict.py
user = User("Alice", 20)
user.name = "Bob"        # ок, имя объявлено
user.email = "a@b.c"     # AttributeError

# если поля все-таки нужно добавлять — просим словарь обратно:
class User:
    __slots__ = ("name", "age", "__dict__")
```

::: out но
с `__dict__` в слотах экономия во многом теряется — это осознанный компромисс,
а не «лучшее из двух»
:::

### Weak references

Слот `__weakref__` тоже нужно запрашивать явно, иначе `weakref.ref(obj)`
поднимет `TypeError`.

::: warn Ломается тише, чем кажется
На weak refs держатся кэши, observer-механизмы и часть библиотек — так они не удерживают
объект от сборки. Без `__weakref__` такой объект просто нельзя туда положить,
и узнаете вы об этом из чужого стека вызовов.
:::

```python/3 weak.py
import weakref

class Node:
    __slots__ = ("value", "__weakref__")
    def __init__(self, value):
        self.value = value

weakref.ref(Node(1))   # теперь работает
```

### Наследование

Самое неприятное место. Слоты не наследуются как «сумма» автоматически: их поведение зависит
от того, что объявлено у каждого класса в цепочке. Достаточно одного наследника без
`__slots__` — и словарь возвращается всем его экземплярам.

{% include "figures/slots-inherit.njk" %}

| Ситуация | Что получаем | Экономия |
| --- | --- | --- |
| Класс со `__slots__`, базовый — `object` | только ячейки | полная{:.ok} |
| Наследник объявил `__slots__ = ()` | ячейки родителя | полная{:.ok} |
| Наследник объявил свои слоты | ячейки родителя + свои | полная{:.ok} |
| Наследник не объявил ничего | ячейки + `__dict__` | потеряна{:.no} |
| Одно имя объявлено дважды в цепочке | дублирующая ячейка | частично теряется{:.no} |

::: stop Множественное наследование
Два родителя, у каждого непустые `__slots__` — и класс просто не создастся:
`TypeError: multiple bases have instance lay-out conflict`.
Непустые слоты плохо сочетаются с миксинами.
:::

## Когда это оправдано

:::: verdict

::: yes Стоит брать
- Миллионы однотипных объектов: точки, события, строки лога, узлы дерева.
- Профилировщик показал, что память уходит именно в экземпляры.
- Набор полей стабилен и известен заранее.
- Хочется, чтобы опечатка в имени поля падала, а не создавала мусорный атрибут.
:::

::: no Не стоит
- Объектов десятки или сотни — выигрыш утонет в шуме.
- Классу нужны миксины с собственными слотами.
- Код или библиотеки дописывают атрибуты снаружи.
- Ставить «на всякий случай», без замера до и после.
:::

::::

Отдельно про скорость: доступ к полю через слот часто чуть быстрее словарного, но выигрыш
легко оказывается нулевым[^3]. Оптимизировать ради него в отрыве от памяти смысла нет.

## Вывод

::: finale
`__slots__` — не стилевое улучшение и не «правильный способ писать классы».
Это точечный обмен гибкости на память.

Есть миллионы одинаковых экземпляров, съедающих доступную память — берите.
Нет замера, показывающего проблему — не берите.
:::

[^1]: Ладно, не каждый: многие built-in и extension types обычного instance `__dict__` не имеют вовсе — `tuple`, `int`, часть типов из C-расширений. Здесь речь про экземпляры обычных пользовательских классов без `__slots__`.
[^2]: Допустима и просто строка, если имя одно: `__slots__ = "name"`.
[^3]: Зависит от версии Python и профиля нагрузки. В горячем цикле разница иногда видна, в обычном коде — почти никогда.
