## Интро

Кортеж выглядит самой простой структурой в языке: неизменяемая последовательность, нечего обсуждать. Но если спросить «сколько стоит создать кортеж», честный ответ будет «смотря какой» — и разброс там не в проценты, а между «одна аллокация» и «вообще ничего не происходит».

Эта заметка смотрит на кортеж с двух сторон сразу:

- **сверху** — какой байт-код выдает компилятор Python;
- **снизу** — что делает код CPython, написанный на C.

Разбираем три строчки, которые в исходнике отличаются только содержимым скобок:

```python three_cases.py
x = ()
x = (1, 2, 3)
x = (a, b, c, d)
```

Спойлер: в рантайме объект создается только в третьем случае.

::: note Версии
Весь вывод получен на CPython 3.12. Байт-код — штука версионно-зависимая: имена и набор инструкций меняются от релиза к релизу, и часть показанного ниже в 3.11 или 3.13 выглядит иначе. Общая механика при этом держится годами.
:::

## Что понадобится

Байт-код, стековая машина и чтение вывода `dis` — отдельная тема, она разобрана в заметке [Disassemble](/notes/python/disassemble/). Дальше считаем известным оттуда:

- компилятор превращает исходник в список простых инструкций, а виртуальная машина выполняет их одну за другой;
- машина эта стековая: переменных и регистров на ее уровне нет, есть стопка значений, и инструкции кладут что-то на вершину или снимают оттуда;
- `dis` показывает получившийся список, по инструкции в строке, с номером строки, смещением, именем инструкции и ее аргументом.

Остается добавить то, что в той заметке не разбиралось.

### Инструкции, которые встретятся

| Инструкция | Что делает |
| --- | --- |
| `RESUME` | Ничего. Метка «сюда можно войти или вернуться», нужна трассировке и генераторам. Стоит в начале каждого модуля и каждой функции начиная с 3.11. |
| `LOAD_CONST i` | Кладет на стек константу номер `i` из таблицы констант |
| `LOAD_NAME i` | Кладет на стек значение переменной с именем номер `i` |
| `LOAD_FAST i` | То же, но для локальных переменных внутри функции — по индексу в массиве, без поиска по словарю |
| `STORE_NAME i` | Снимает вершину стека и записывает в переменную |
| `BUILD_TUPLE n` | Снимает `n` верхних значений и кладет обратно кортеж из них |
| `RETURN_CONST i` | Возвращает константу номер `i`. Новая инструкция в 3.12 — раньше на это уходила пара `LOAD_CONST` + `RETURN_VALUE` |

### Таблица констант

Все литералы, которые компилятор смог посчитать заранее, складываются в массив `co_consts` — он лежит прямо внутри объекта кода:

```python consts.py
code = compile("x = (1, 2, 3)", "<s>", "exec")
code.co_consts
```

::: out
((1, 2, 3), None)
:::

Эти объекты создаются один раз при компиляции модуля и живут до конца его жизни. `LOAD_CONST` не создает ничего — только берет готовый указатель.

Имена переменных хранятся отдельно, в `co_names`, и там уже не объекты, а строки:

```python names.py
compile("x = (a, b, c, d)", "<s>", "exec").co_names
```

::: out
('a', 'b', 'c', 'd', 'x')
:::

### Как устроен кортеж в C

Минимум, без которого не обойтись:

```c tupleobject.h
typedef struct {
    PyObject_VAR_HEAD        // refcount, тип, длина
    PyObject *ob_item[1];    // массив указателей на элементы
} PyTupleObject;
```

Два важных следствия:

- Кортеж хранит **указатели** на объекты, а не сами значения. В CPython у числа нет «голой» формы: даже `1` — это полноценный объект с заголовком (счетчик ссылок, тип), так что положить в слот можно только его адрес. Малые числа от −5 до 256 к тому же существуют в одном экземпляре на весь интерпретатор, так что в `(1, 1)` оба слота — указатели на один и тот же объект.
- Массив лежит **внутри** объекта, одним куском с заголовком. Запись `ob_item[1]`[^1] — прием из C: объявляем массив из одного элемента, а памяти выделяем столько, сколько нужно под все. Так можно, потому что кортеж неизменяем и свой размер узнает при рождении.

::: tip Сравните со списком
У списка на этом месте `PyObject **ob_item` — указатель на отдельно выделенный буфер. Список умеет расти, а значит буфер должен уметь переезжать; сам же объект списка переезжать не может, на него держат ссылки. Отсюда две аллокации вместо одной.
:::

### Счетчик ссылок

CPython освобождает объекты по счетчику ссылок: каждая новая ссылка увеличивает `ob_refcnt`, каждая исчезнувшая — уменьшает, на нуле объект умирает. Макросы называются `Py_INCREF` и `Py_DECREF`.

Из этого есть важный для нас вывод: когда значение переезжает со стека внутрь кортежа, счетчик можно **не трогать**. Стек владел ссылкой, стек ее отдал, кортеж принял — владелец сменился, количество владельцев не изменилось. В исходниках CPython это называется «украсть ссылку» (*steal a reference*), и сэкономленные пары `INCREF`/`DECREF` — вполне ощутимая величина.

## Случай 1: пустой кортеж

```python empty.py
import dis

dis.dis("x = ()")
```

::: out
```
  0           0 RESUME                   0

  1           2 LOAD_CONST               0 (())
              4 STORE_NAME               0 (x)
              6 RETURN_CONST             1 (None)
```
:::

Инструкций, относящихся к делу, ровно две: взять готовую константу, записать в переменную. **В рантайме не создается ничего.**

Больше того: пустой кортеж в CPython существует в единственном экземпляре на весь интерпретатор. Это статический объект, вшитый прямо в бинарник.

```python singleton.py
() is ()
```

::: out
True
:::

С версии 3.12 он еще и **бессмертный** (PEP 683) — его счетчик ссылок прибит к максимальному значению и не меняется вообще:

```python immortal.py
import sys

sys.getrefcount(())      # пустой кортеж
sys.getrefcount(None)    # для сравнения
```

::: out
4294967295
4294967295
:::

::: note Зачем бессмертие
До 3.12 каждое обращение к `None`, `True` или пустому кортежу дергало счетчик вверх и вниз. Это запись в память — а значит, ядра процессора в многопоточной программе постоянно отбирали друг у друга одну и ту же кеш-линию, и copy-on-write после `fork` копировал страницы, в которых «изменились» только счетчики. Теперь такие объекты доступны только на чтение.
:::

**Итого:** одна загрузка указателя на вечный объект, одна запись в словарь модуля — обычный `dict`, где модуль хранит свои глобальные переменные (тот самый `globals()`), так что `STORE_NAME` здесь равносилен `globals()["x"] = ()`. Ни аллокаций, ни работы со счетчиками.

## Случай 2: кортеж из литералов

```python literals.py
import dis

dis.dis("x = (1, 2, 3)")
```

::: out
```
  0           0 RESUME                   0

  1           2 LOAD_CONST               0 ((1, 2, 3))
              4 STORE_NAME               0 (x)
              6 RETURN_CONST             1 (None)
```
:::

Байт-код **буквально тот же самый**, что и у пустого кортежа. Никакого `BUILD_TUPLE` здесь нет: компилятор увидел, что все элементы — литералы, собрал кортеж во время компиляции и положил в `co_consts`. В рантайме остается `Py_INCREF` и запись указателя.

Это называется свертка констант, и работает она только пока внутри одни константы: числа, строки, `None`, вложенные кортежи из таких же. Одна переменная внутри — и схема ломается, см. следующий раздел.

Побочный эффект: внутри одного объекта кода компилятор еще и дедуплицирует константы.

```python dedup.py
a = (1, 2, 3)
b = (1, 2, 3)
a is b
```

::: out
True
:::

::: warn Это не интернирование
Кортежи в Python не интернируются — то есть интерпретатор не держит таблицу «канонических» кортежей, как делает для строк (`sys.intern`). Выше сработало другое: компилятор положил в таблицу констант **один** объект и сослался на него из двух мест. Стоит собрать тот же литерал отдельно — и объект будет уже другой.
:::

```python not_interned.py
a = (1, 2, 3)
c = eval("(1, 2, 3)")
a is c
```

::: out
False
:::

Полагаться на `is` для кортежей нельзя ни в какую сторону — это деталь реализации компилятора, а не гарантия языка.

::: note Почему со списком так нельзя
`x = [1, 2, 3]` всегда компилируется в `BUILD_LIST` с настоящей аллокацией. Список изменяем: положи его в константы — и первый же `x.append(4)` испортит константу для всех последующих выполнений этой строки. Неизменяемым кортежем делиться безопасно, изменяемым списком — нет.
:::

**Итого:**

- Выполнение строки с кортежем из литералов стоит одинаково при любой длине — одна загрузка готового указателя. Кортеж из тысячи чисел исполняется так же быстро, как пустой.
- Платит он в другом месте: объект собирается один раз при компиляции (или при загрузке `.pyc`) и все время жизни кода занимает память — заголовок плюс по указателю на элемент. У пустого кортежа нет и этого: он один на весь интерпретатор.

## Случай 3: кортеж из переменных

```python variables.py
import dis

dis.dis("x = (a, b, c, d)")
```

::: out
```
  0           0 RESUME                   0

  1           2 LOAD_NAME                0 (a)
              4 LOAD_NAME                1 (b)
              6 LOAD_NAME                2 (c)
              8 LOAD_NAME                3 (d)
             10 BUILD_TUPLE              4
             12 STORE_NAME               4 (x)
             14 RETURN_CONST             0 (None)
```
:::

Вот здесь наконец происходит настоящая работа.

### Четыре LOAD_NAME

Каждая инструкция находит переменную и кладет указатель на ее значение на стек, увеличивая счетчик ссылок. Стек растет снизу вверх:

```
                             ┌───┐
                       ┌───┐ │ d │ ← вершина
                 ┌───┐ │ c │ │ c │
           ┌───┐ │ b │ │ b │ │ b │
    пусто  │ a │ │ a │ │ a │ │ a │
           └───┘ └───┘ └───┘ └───┘
```

`LOAD_NAME` ищет имя по трем словарям подряд: локальные, глобальные, встроенные. Это хеш-таблицы, то есть не бесплатно.

А вот внутри функции компилятор знает все локальные имена заранее и выдает вместо этого `LOAD_FAST` — чтение из массива по индексу:

```python in_function.py
import dis

def f(a, b, c, d):
    return (a, b, c, d)

dis.dis(f)
```

::: out
```
  3           0 RESUME                   0

  4           2 LOAD_FAST                0 (a)
              4 LOAD_FAST                1 (b)
              6 LOAD_FAST                2 (c)
              8 LOAD_FAST                3 (d)
             10 BUILD_TUPLE              4
             12 RETURN_VALUE
```
:::

Отсюда классический совет держать горячий код в функции, а не на уровне модуля: там переменные становятся локальными, и каждое обращение к ним — индекс в массиве локальных переменных кадра (номер слота компилятор вычислил заранее), а не поиск по строке в словаре модуля (`globals()`) и встроенных имен. Численный замер — в примечании[^2].

### BUILD_TUPLE 4

Аргумент говорит, сколько значений забрать со стека. Внутри — вызов `_PyTuple_FromArraySteal`, который делает четыре вещи.

**1. Взять память.** Сначала CPython заглядывает во **freelist** — стопку уже умерших кортежей ровно этой длины. Отдельная стопка на каждый размер от 1 до 19, до 2000 штук в каждой. Если там что-то есть, блок просто снимается с вершины, и до аллокатора дело не доходит.

```python freelist.py
def mk(a, b, c, d):
    return (a, b, c, d)     # BUILD_TUPLE 4

t = mk(1, 2, 3, 4)
addr = id(t)
del t                       # кортеж умер — блок ушел во freelist

t = mk(4, 3, 2, 1)
print(id(t) == addr)
```

::: out
True
:::

Другой кортеж — тот же адрес: новый кортеж из четырех элементов забрал блок, который только что освободил предыдущий. Собирать их приходится функцией: литерал `(1, 2, 3, 4)` лежит в таблице констант, не умирает и во freelist не попадает.

::: note Почему у кортежей freelist по размерам
Блок памяти под кортеж из четырех элементов годится только под другой кортеж из четырех: массив-то лежит внутри объекта. У списка заголовок всегда одного размера, поэтому freelist у него один на всех — зато буфер туда не попадает никогда.
:::

Если в стопке для этой длины пусто — или длина больше 19, и стопки нет вовсе, — обычная аллокация: заголовок плюс четыре указателя, одним куском, плюс служебный заголовок сборщика мусора спереди.

**2. Заполнить заголовок.** Счетчик ссылок в единицу, тип — `PyTuple_Type`, длина — 4.

**3. Перенести указатели** со стека в слоты. Без единого `INCREF` — это та самая кража ссылок: четыре пары операций со счетчиками просто не выполняются.

**4. Поставить на учет сборщика мусора.** Кортеж содержит ссылки на другие объекты, значит может оказаться частью цикла, значит сборщик обязан уметь его обойти.

Стек после инструкции:

```
    ┌──────────────┐
    │ (a, b, c, d) │ ← один объект вместо четырех значений
    └──────────────┘
```

### STORE_NAME

Снять кортеж с вершины и записать в словарь модуля под ключом `x`. Ссылка снова переезжает без изменения счетчика.

**Итого:** четыре поиска по словарям, одна аллокация (или снятие блока с freelist), заполнение четырех слотов, регистрация в GC.

## Сводка

| | `()` | `(1, 2, 3)` | `(a, b, c, d)` |
| --- | --- | --- | --- |
| Инструкции построения | `LOAD_CONST` | `LOAD_CONST` | 4 × `LOAD_NAME` + `BUILD_TUPLE` |
| Когда создан объект | при старте CPython | при компиляции | при каждом выполнении |
| Аллокаций в рантайме | нет{:.ok} | нет{:.ok} | одна, или ноль из freelist |
| Работа со счетчиками | нет, бессмертный{:.ok} | один `INCREF` | четыре `INCREF` на загрузках |
| Объект общий | один на интерпретатор | один на объект кода | новый каждый раз |

::: finale
Стоимость кортежа определяется не длиной, а происхождением элементов.

Литерал из констант бесплатен в рантайме при любом размере — он собран задолго до запуска. А `(a, b)` в горячем цикле каждый раз платит за поиск имен и сборку объекта, пусть freelist и делает эту плату небольшой.
:::

[^1]: **Как читать `PyObject *ob_item[1]`.** В C `[]` связывается сильнее, чем `*`, поэтому объявление читается от имени наружу:

    ```
    ob_item            ob_item — это
    ob_item[1]         массив из одного элемента,
    *ob_item[1]        и элемент — указатель
    PyObject           на PyObject
    ```

    То есть это «массив из одного `PyObject *`», а не «указатель на массив». Каждый элемент — один указатель, 8 байт на 64-битной машине.

    **Почему `[1]` не ограничивает размер.** Структура описывает только начало блока памяти. Для кортежа из четырех элементов CPython выделяет не `sizeof(PyTupleObject)`, а заголовок плюс четыре указателя — одним куском:

    ```
    (a, b, c, d)
    ┌──────────────┐
    │ ob_refcnt    │  ┐
    │ ob_type      │  ├ PyObject_VAR_HEAD
    │ ob_size = 4  │  ┘
    ├──────────────┤
    │ ob_item[0] ──┼──→ a   ← объявлен в структуре
    │ ob_item[1] ──┼──→ b   ┐
    │ ob_item[2] ──┼──→ c   ├ за пределами [1],
    │ ob_item[3] ──┼──→ d   ┘ но память выделена
    └──────────────┘
    ```

    Границы массивов C не проверяет: `ob_item[3]` — это просто «адрес, где начинается массив, плюс 3 × 8 байт» (указатель на 64-битной машине занимает 8 байт). Объявленный размер `[1]` в этом расчете не участвует. Память выделена — значит, по этому адресу лежит настоящий указатель. Настоящую длину хранит `ob_size`, и границы проверяет уже сам CPython: `t[10]` дает `IndexError`.

    Это же зашито в объект типа: у `PyTuple_Type` `tp_basicsize = sizeof(PyTupleObject) - sizeof(PyObject *)`, а `tp_itemsize = sizeof(PyObject *)`. Аллокатор считает `basicsize + n * itemsize`: фальшивый слот `[1]` вычитается, `n` настоящих добавляются. Поэтому `()` — это один заголовок, без слотов вовсе.

    **Почему `[1]`, а не `[0]` или `[]`.** Это старый прием, известный как *struct hack*. Массив нулевой длины `[0]` в стандартном C запрещен. Пустые скобки `[]` — последнее поле структуры в виде массива без размера (в стандарте это называется *flexible array member*), правильный способ из C99, но публичные заголовки CPython должны компилироваться еще и как C++, где такой записи в стандарте нет. А `[1]` законен везде, и индексацию за его пределами все компиляторы понимают так, как ожидается. Формально по стандарту выход за индекс 0 — неопределенное поведение, на практике — многолетняя конвенция.

    **Почему так можно кортежу и нельзя списку.** Массив живет в одном блоке с заголовком, значит его размер фиксируется при создании объекта. Кортеж длину не меняет — ему подходит. Списку нужно расти, поэтому у него `PyObject **ob_item` — указатель на отдельный буфер, который можно перевыделить.

[^2]: Замер: 5 млн выполнений `x = (a, b, c, d)` в цикле, лучшее из 5 запусков. Время ориентировочное — на другой машине абсолютные цифры будут другими, соотношения примерно те же.

    | Где выполняется код | Инструкции | 3.9 | 3.12 |
    | --- | --- | --- | --- |
    | уровень модуля | `LOAD_NAME` ×4 | 0.219 с | 0.161 с |
    | функция, переменные глобальные | `LOAD_GLOBAL` ×4 | 0.183 с | 0.092 с |
    | функция, переменные — параметры | `LOAD_FAST` ×4 | 0.096 с | 0.071 с |

    Что показывают цифры. `LOAD_FAST` быстрее всех: на 3.12 код на уровне модуля медленнее той же строки в функции примерно в 2,3 раза. `LOAD_GLOBAL` с 3.11 кеширует, где имя лежало в прошлый раз, и проверяет только метку версии словаря — поэтому на 3.12 он вдвое быстрее, чем на 3.9, и почти догнал `LOAD_FAST`. У `LOAD_NAME` такого кеша нет, и уровень модуля остается самым медленным. Сборка кортежа одинакова во всех строках, так что чистая разница в доступе к переменным еще больше, чем видно в таблице.
