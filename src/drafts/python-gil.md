## Интро

**GIL** (Global Interpreter Lock) - мьютекс внутри CPython. Поток, который хочет исполнять байткод, должен его держать. Поэтому в стандартной сборке два потока с чистым Python-кодом не работают одновременно, а по очереди делят одно ядро, даже если ядер шестнадцать.

Важно, что именно блокирует GIL:

- **исполнение байткода** - да, один поток за раз;
- **ожидание I/O** - нет: `socket.recv`, `file.read`, `time.sleep` отпускают GIL на время системного вызова;
- **тяжелые C-расширения** - как решит автор: numpy, hashlib, zlib отпускают GIL на долгих операциях.

Отсюда многолетнее правило: потоки - для I/O-bound, процессы - для CPU-bound.

```python cpu_bound.py
import statistics
import timeit
from concurrent.futures import ThreadPoolExecutor

def count(n):
    while n:
        n -= 1

N = 50_000_000

def sequential():
    count(N)
    count(N)

def threaded():
    with ThreadPoolExecutor(2) as ex:
        ex.submit(count, N)
        ex.submit(count, N)

for name, fn in [("последовательно", sequential), ("два потока", threaded)]:
    times = timeit.repeat(fn, number=1, repeat=5)
    print(f"{name:<16} min {min(times):.2f} с, медиана {statistics.median(times):.2f} с")
```

::: out
```
последовательно  min 0.77 с, медиана 0.77 с
два потока       min 0.78 с, медиана 0.78 с
```
:::

`timeit.repeat` запускает каждый вариант пять раз. Минимум - время почти без помех: фоновые процессы могут только замедлить прогон, но не ускорить. Медиана - типичный прогон. По обоим числам два потока отработали за то же время, что и последовательный вызов - ускорения нет.

Потоки по очереди держат GIL, поэтому вычисления в них не идут параллельно. На free-threaded сборке тот же файл без изменений отрабатывает вдвое быстрее - см. [ниже](#путь-2-free-threading). Этот пример и есть вся история в миниатюре.


## Почему именно GIL

Потоки появились в Python в начале 90-х, когда многоядерных машин на столе ни у кого не было. Интерпретатор держит кучу глобального состояния, а у каждого объекта есть счетчик ссылок `ob_refcnt`, который меняется на каждом присваивании и вызове. Сделать все это потокобезопасным можно двумя способами:

- **мелкие блокировки** - атомарные инкременты счетчиков, замок на каждый `dict` и `list`, замки на аллокаторе;
- **один большой замок** - на весь интерпретатор.

Второй вариант проще, быстрее для однопоточного кода и упрощает жизнь авторам C-расширений: пока держишь GIL, можно не думать о гонках. Выбрали его.

::: note Почему это важно
GIL - не свойство языка Python, а деталь реализации CPython. У Jython и IronPython GIL не было никогда. У PyPy он есть.
:::


## Цена решения

Лет десять GIL никому особо не мешал: ядро было одно. Потом частота процессоров перестала расти, и производители начали наращивать число ядер (Herb Sutter, «The Free Lunch Is Over», 2005). Python оказался языком, который по умолчанию использует одно ядро из восьми.

Обходные пути были, но у каждого своя цена:

| Способ | Параллелит Python-код | Цена |
|---|---|---|
| `threading` | нет {:.no} | только I/O |
| `multiprocessing` | да {:.ok} | старт процесса, pickle на каждый аргумент и результат, память x N |
| C-расширение, отпускающее GIL | да {:.ok} | надо писать на C / Cython / Rust |
| `asyncio` | нет {:.no} | решает другую задачу: ожидание, а не вычисления |

Особенно больно стало с приходом ML. Сэм Гросс (Meta), один из разработчиков PyTorch, в PEP 703 описывает типичную картину: загрузка данных, препроцессинг, распределенное обучение - все это хочется делать потоками в одном процессе, с общей памятью под тензоры, а приходится городить процессы и сериализацию.


## Попытки убрать GIL

GIL пытались убрать с середины 90-х. Все попытки до 2021 года закончились ничем.

| Год | Что | Итог |
|---|---|---|
| 1996 | Грег Стейн, патч «free threading» для Python 1.4 | однопоточный код примерно вдвое медленнее, отказались |
| 2007 | Гвидо, пост «It isn't Easy to Remove the GIL» | условие: однопоточный код и расширения не должны пострадать |
| 2009 | Unladen Swallow (Google) | в планах было убрать GIL, проект закрыли |
| 2010 | новый GIL в 3.2 (Антуан Питру) | GIL не убрали, но переключение стало по времени, `sys.setswitchinterval()`, 5 мс |
| 2016 | Gilectomy (Ларри Хастингс) | без GIL работало, но медленно; заброшен |
| 2021 | nogil - форк 3.9 от Сэма Гросса | впервые приемлемая скорость, основа PEP 703 |

Проблема у всех ранних попыток одна: если заменить GIL на атомарные операции со счетчиками ссылок, однопоточный код - а его подавляющее большинство - замедляется на десятки процентов. Условие Гвидо 2007 года никто не мог выполнить.

::: more Как nogil обходит проблему счетчиков
- **biased reference counting** - у объекта два счетчика: локальный для потока-владельца (обычный инкремент, без атомиков) и общий для остальных (атомарный). Большинство объектов живет и умирает в одном потоке;
- **бессмертные объекты** (PEP 683, 3.12) - `None`, `True`, маленькие числа, интернированные строки вообще не трогают счетчик;
- **отложенный подсчет** - для функций, модулей, типов, которые трогают все потоки;
- **mimalloc** вместо pymalloc - потокобезопасный аллокатор;
- **замки на объектах** - у `dict`, `list` и прочих свой легкий мьютекс, критические секции в C API.
:::


## Путь 1: субинтерпретаторы

Субинтерпретаторы были в C API всегда (`Py_NewInterpreter`, со времен Python 1.5). Ими пользовался, например, `mod_wsgi`, чтобы изолировать приложения в одном процессе Apache. Но GIL был общим на процесс, так что параллельности это не давало.

Эрик Сноу, core-разработчик CPython, с 2015 года вел проект по изоляции интерпретаторов друг от друга: вынести глобальное состояние в структуру интерпретатора, перевести встроенные модули на многофазную инициализацию (PEP 489), сделать типы кучи вместо статических. Итог:

- **3.12** - PEP 684: у каждого интерпретатора может быть свой GIL. Только из C API.
- **3.13** - приватный модуль `_interpreters`, бэкпорт на PyPI (`interpreters-pep-734`).
- **3.14** - PEP 734: модуль `concurrent.interpreters` в stdlib и `InterpreterPoolExecutor` в `concurrent.futures`.

```python/3 interp.py @3.14
from concurrent import interpreters

interp = interpreters.create()
interp.exec("print('hello from', __name__)")
interp.close()
```

Модель ближе к процессам, чем к потокам: у каждого интерпретатора свои модули, свои `sys.modules`, свой `__main__`, свои объекты. Передать объект напрямую нельзя - только через очередь или вызов, и только «разделяемые» типы (`None`, `bool`, `int`, `float`, `str`, `bytes`, кортежи из них, `memoryview`). Все остальное копируется через pickle.

```python cpu_interp.py @3.14
from concurrent.futures import InterpreterPoolExecutor

def count(n):
    while n:
        n -= 1

with InterpreterPoolExecutor(4) as ex:
    list(ex.map(count, [50_000_000] * 4))
```

Интерфейс тот же, что у `ProcessPoolExecutor`, но все живет в одном процессе: старт быстрее, памяти меньше.

::: warn Ограничения
- C-расширение должно поддерживать изоляцию (многофазная инициализация, нет глобального состояния). Иначе импорт в субинтерпретаторе падает с `ImportError`. Сверить статус numpy и прочих популярных библиотек на момент публикации.
- Общих объектов нет. Если задача - «много потоков работают с одним большим графом объектов», субинтерпретаторы не помогут.
:::


## Путь 2: free-threading

Сэм Гросс показал nogil в 2021, PEP 703 подал в 2023. Steering Council принял его в июле 2023 с оговоркой: делать постепенно и быть готовыми откатить.

- **Фаза I** (3.13, октябрь 2024) - экспериментальная сборка `--disable-gil`, бинарник `python3.13t`. Однопоточный код заметно медленнее: в этой сборке был выключен специализирующий интерпретатор (PEP 659).
- **Фаза II** (3.14, октябрь 2025, PEP 779) - сборка официально поддерживается, специализация включена, однопоточное замедление упало до единиц процентов. По умолчанию GIL все еще есть.
- **Фаза III** - free-threading по умолчанию. Сроки не назначены, решение за Steering Council.

Код под эту сборку писать иначе не нужно: те же `threading` и `ThreadPoolExecutor`. Сама по себе программа параллельной не становится - пока не создан второй поток, работает один. Меняется только то, что созданные потоки больше не ждут друг друга. Тот же `cpu_bound.py` из интро:

```bash terminal
python3.14  cpu_bound.py
python3.14t cpu_bound.py
```

::: out
```
# python3.14
последовательно  min 0.77 с, медиана 0.77 с
два потока       min 0.78 с, медиана 0.78 с

# python3.14t
последовательно  min 0.80 с, медиана 0.80 с
два потока       min 0.40 с, медиана 0.41 с
```
:::

Два потока - ровно в два раза быстрее. Цена - однопоточный код: 0.80 с против 0.77 с, примерно на 4% медленнее.

Проверить, в какой сборке работаешь:

```python gil_check.py @3.14
import sys
import sysconfig

print(sysconfig.get_config_var("Py_GIL_DISABLED"))  # 1 - сборка без GIL
print(sys._is_gil_enabled())                        # GIL включен прямо сейчас?
```

Две проверки нужны, потому что даже в free-threaded сборке GIL может вернуться. Если импортировать C-расширение, которое не объявило поддержку (слот `Py_mod_gil` = `Py_MOD_GIL_NOT_USED`), интерпретатор включит GIL обратно и выдаст `RuntimeWarning`. Форсировать можно через `PYTHON_GIL=0` или `-X gil=0`.

::: stop Гонки теперь настоящие
Без GIL `i += 1` из двух потоков теряет инкременты не только теоретически. Раньше GIL случайно прикрывал многие гонки в прикладном коде, теперь они всплывут. `dict` и `list` сами не сломаются (на них свои замки), а вот инварианты вашего кода - запросто. См. пост про `disassemble`: `+=` - это несколько инструкций.
:::


## Два пути: что выбрать

| | Субинтерпретаторы | Free-threading |
|---|---|---|
| Версия | 3.14 (`concurrent.interpreters`) | 3.13t экспериментально, 3.14t поддерживается |
| Сборка | обычная | отдельная, `python3.14t` |
| Общие объекты | нет, копирование {:.no} | да {:.ok} |
| Гонки в прикладном коде | как у процессов - изоляция {:.ok} | как в Java/C++ - ваша забота {:.no} |
| C-расширения | нужна изоляция модуля | нужна потокобезопасность + `Py_mod_gil` |
| Похоже на | `multiprocessing` в одном процессе | обычные потоки в других языках |

Пути не конкурируют: субинтерпретаторы работают и в free-threaded сборке. Первое - про изоляцию, второе - про общую память.


## Как оно сейчас (осень 2026)

- Бинарники `3.14t` есть в официальных установщиках, в `uv` и `pyenv`; CI-образы с free-threaded сборкой - норма для крупных библиотек.
- Экосистема подтягивается: numpy, Cython, PyO3 и другие выпускают free-threaded колеса. Статус конкретных пакетов - трекер py-free-threading.github.io.
- Однопоточная цена сборки без GIL - единицы процентов, плюс больше памяти.
- `concurrent.interpreters` живой, но библиотек поверх него почти нет; главное ограничение - C-расширения без поддержки изоляции.
- Нерешенное: когда (и будет ли) Фаза III, что делать с расширениями, которые никто не перепишет, как учить людей писать потокобезопасный Python.

::: finale Итог
GIL никуда не делся из стандартной сборки, но перестал быть приговором. Нужна изоляция и простая модель - субинтерпретаторы. Нужна общая память - free-threaded сборка, с полным набором проблем многопоточного программирования в придачу.
:::
