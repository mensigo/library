Слои и кеш сборки

4 мин16 октОбразыDockerfileКеш

Каждая инструкция Dockerfile, меняющая файлы, дает слой. Сборщик кеширует слои по порядку, поэтому от порядка инструкций зависит, сколько пересобирается после правки одной строки.

Слой - это дифф #

Слой - зафиксированный набор изменений файловой системы относительно предыдущего состояния: какие файлы добавлены, изменены, удалены. Как коммит в git, только для ФС.

Слой дают инструкции, которые меняют файлы: RUN, COPY, ADD. Слои складываются стопкой, и процесс в контейнере видит одно обычное дерево, ничего не зная о слоях.

Порядок инструкций #

Сборщик идет по Dockerfile сверху вниз и берет слой из кеша, пока инструкция и ее входные файлы не изменились. Первый же промах пересобирает все, что ниже.

былоdockerfile
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
сталоdockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]

Слева правка в app.py ломает кеш уже на COPY . ., и зависимости ставятся заново. Справа они лежат слоем выше кода и переживают любую его правку:

терминалbash
docker build -t app .
stdoutвывод 
 => CACHED [2/5] WORKDIR /app
 => CACHED [3/5] COPY requirements.txt .
 => CACHED [4/5] RUN pip install -r requirements.txt
 => [5/5] COPY . .
.dockerignore

COPY . . берет и .git, и виртуальное окружение. Любая их перемена тоже ломает кеш - их стоит перечислить в .dockerignore.

Удаление не уменьшает образ #

Удалить файл из нижнего слоя нельзя: слои read-only. Новый слой только кладет поверх маркер «скрыт» (whiteout), а сами байты остаются в образе. Поэтому RUN rm отдельной строкой ничего не экономит: чистить нужно в той же инструкции, где мусор появился, или собирать образ в несколько стадий.

Итог

Что меняется редко - выше, что часто - ниже. Тогда правка кода пересобирает один тонкий слой, а не все окружение.
